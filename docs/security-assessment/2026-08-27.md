# Prime Dispatch Prototype Security Assessment

Assessment date: 2026-08-27  
Reviewed commit: `9414ec75371aeef8cfca6c27fb9770725c437797` (`main`)  
Assessment type: static application and configuration review with deterministic test and dependency-audit validation

## Executive summary

Prime Dispatch has a notably strong control plane for a prototype. The reviewed code consistently treats Discord input, model output, repository contents, Git references, IPC peers, cached runtime files, and cleanup targets as hostile. Owner identity and the original delivery route are checked before job operations; confirmation is bound to the immutable resolved request; subprocess arguments are not passed through a shell; the inference broker fixes its upstream and model; the Prime runtime is content verified; SQLite statements are parameterized; and destructive cleanup re-proves target identity before deletion.

The assessment confirmed one high-severity weakness: real Prime work runs as the OpenClaw operating-system user without filesystem, process, or network isolation. A malicious or compromised allowlisted repository can therefore turn model-controlled IPython execution into access to everything available to that user, including OpenClaw state, credentials, repositories, local control-plane data, and outbound network access. The repository documents this limitation accurately, and the Discord adapter admits only repositories marked as fixtures, but `fixture` is a trusted configuration label rather than an enforceable containment boundary. This blocks safe use with repositories whose content or dependencies are not fully trusted.

A second, low-severity supply-chain finding concerns mutable GitHub Actions references. It has limited current impact because workflow permissions are read-only, the repository is public, and the workflow does not publish artifacts or receive production secrets.

No confirmed SQL/command injection, object-level authorization bypass, SSRF, path traversal, unsafe archive extraction, secret disclosure, or known vulnerable dependency was identified in the reviewed revision. One deployment-dependent authorization concern remains unverified: the standalone CLI intentionally trusts its local caller, so the owner-only plugin boundary is bypassable if a non-owner OpenClaw session can invoke arbitrary local processes. The deployed OpenClaw tool policy was not present in this repository and must be checked separately.

## Application context and threat model

### What the application does

Prime Dispatch is a TypeScript control plane that accepts an owner-authorized task and selected Git repository, resolves an immutable base commit, launches a detached worker, creates root and optional child worktrees, runs Prime Agent, brokers scoped model inference, executes trusted verification gates, commits successful changes, and preserves durable evidence. An OpenClaw plugin exposes the workflow to Discord through owner-only tools, confirmation commands, status cards, and lifecycle notifications.

### Principal users and assets

- The operator is the authenticated OpenClaw/Discord owner.
- Prime and its child agents are model-controlled code-editing processes.
- Primary assets are OpenClaw OAuth/provider credentials, account and routing metadata, local source repositories, Git history, the control-plane SQLite database, durable evidence, host configuration, the pinned Prime runtime, and the availability and integrity of the OpenClaw host.

### Trust boundaries

The code and documentation explicitly classify Discord text, model output, repository contents, Git refs, IPC messages, runtime archives, and filesystem projections as untrusted. Host configuration, OpenClaw's trusted sender context, the operating-system account, the reviewed runtime artifact hash, and the release-building process are treated as trusted.

The most important boundary is currently incomplete: the model-driven process is separated logically by a worktree, private HOME, scoped inference token, and constrained environment, but it is not separated by a different OS identity, filesystem namespace, network namespace, container, or virtual machine.

### Entry points and privileged sinks reviewed

- OpenClaw tools, Discord commands, interactive component handler, and notification delivery in `openclaw-plugin/src/`.
- CLI arguments for start, resume, status, steer, cancel, result, cleanup, migration, runtime build, and installation in `src/cli.ts` and `src/openclaw-host.ts`.
- Worker Unix-socket IPC in `src/ipc.ts`, `src/worker.ts`, and `src/worker-identity.ts`.
- Repository and Git operations in `src/repository.ts`, `src/execution.ts`, `src/child-git.ts`, and `src/process.ts`.
- Prime RPC/SDK execution, model configuration, and child hosting in `src/agent.ts`, `src/prime-sdk.ts`, `src/prime-runtime.ts`, and `src/child-host-bridge.ts`.
- HTTP inference brokering in `src/inference.ts`.
- SQLite authority, projection repair, artifacts, migrations, recovery, and cleanup in `src/store.ts`, `src/sqlite.ts`, `src/migrations/`, `src/resume.ts`, and `src/cleanup.ts`.
- Runtime artifact creation/extraction and OpenClaw installation in `src/prime-runtime-artifact.ts`, `src/openclaw-install.ts`, and `src/openclaw-auth.ts`.
- Dependency manifests, lockfiles, and `.github/workflows/ci.yml`.

## Confirmed findings

### PD-01: Model-controlled execution has the OpenClaw OS user's filesystem and network authority

Severity: **High**  
Confidence: **High**  
Affected component: `unsafe-local` execution backend, Prime RPC/SDK sessions, and child-agent execution  
Locations:

- `src/execution.ts:63` (`UnsafeLocalExecutionBackend` creates only a Git worktree)
- `src/agent.ts:176` (Prime RPC is spawned with a working directory and environment, but no OS containment)
- `src/prime-sdk.ts:147` and `src/prime-sdk.ts:157` (SDK sessions expose the `ipython` tool)
- `src/prime-runtime.ts:58` and `src/prime-runtime.ts:72` (RPC launch explicitly enables `ipython`)
- `src/policy.ts:15` (the reduced environment is defense in depth, not a filesystem or network boundary)

#### Vulnerability

The application executes model-directed Python/tool activity as the same operating-system user that runs the trusted worker and OpenClaw. `cwd`, a private HOME, a reduced environment, process-group teardown, Git wrappers, and a scoped model token constrain accidental behavior, but none prevents the process from opening arbitrary same-user files, connecting to arbitrary network destinations, modifying OpenClaw state, or spawning a process that escapes the intended worktree.

The adapter's fixture-only check reduces exposure but does not enforce the security property. `fixture` is a boolean from trusted host configuration; the selected repository is not placed in a sandbox and its content is not proven harmless. An allowlisted repository can become hostile through a malicious pull request, compromised dependency, poisoned generated file, or indirect prompt injection that induces Prime to execute attacker-selected code.

#### Concrete data flow

1. The owner submits a task and repository through `prime_start`; the plugin supplies host-owned repository policy and requires confirmation.
2. The dispatcher resolves the repository and launches a worker using `UnsafeLocalExecutionBackend`.
3. The worker creates a worktree and starts Prime. Both the JSONL backend and the SDK backend give Prime the `ipython` tool.
4. Repository content and the requested task influence model decisions and Python/tool input.
5. The tool process runs as the OpenClaw OS user. Its working directory is the worktree, but normal absolute-path filesystem access and normal host networking remain available.
6. Attacker-directed code can read or alter any resource available to that user and send recovered data over the network. Likely targets include OpenClaw configuration/state, OAuth material, SSH/cloud credentials, other repositories, the Prime Dispatch SQLite database, confirmation files, worker control metadata, and installed plugin files.

The same path applies to child sessions because child worktrees provide Git isolation, not an OS security boundary.

#### Exploitability preconditions

- An owner confirms a job against a host-configured repository marked as a fixture, or explicitly enables unsafe execution for a live repository through the standalone CLI.
- Attacker-controlled repository content, dependency behavior, or prompt material causes Prime to execute malicious Python or another process.
- The desired target is accessible to the OpenClaw OS user, or the host allows useful outbound connections.

The finding is rated High rather than Critical because the remote Discord boundary is owner-only, repository selection is host-configured, and a confirmed job is required. Once those preconditions are met, confidentiality, integrity, and availability impact extend across the entire OpenClaw user account.

#### Realistic impact

- Theft and exfiltration of OpenClaw/provider credentials or other same-user secrets.
- Modification of the control database, authorization projections, confirmations, installed plugins, or source repositories.
- Persistence through same-user startup/configuration locations or repository Git hooks.
- Network access to internal or cloud services reachable from the host, including metadata services where applicable.
- Host resource exhaustion or background processes that outlive the intended Prime process group.

#### Remediation

Do not admit real Prime jobs for any repository whose entire content and dependency behavior are not trusted until a contained execution backend exists. Keep `unsafe-local` limited to disposable developer fixtures and make that limitation mechanically hard to misconfigure.

Implement a `ContainedExecutionBackend` that launches every root and child agent in a separate security domain with at least these properties:

- a dedicated unprivileged UID with no access to the OpenClaw home/state, Prime Dispatch state root, SSH/cloud credentials, source checkouts, or the worker process;
- a read-only base filesystem with only the assigned worktree writable;
- no host PID, IPC, or user namespace authority; no new privileges; dropped capabilities; and bounded PIDs, CPU, memory, and disk;
- default-deny egress, allowing only the scoped inference broker through a deliberately exposed socket or isolated network route;
- no mount of the provider credential, host configuration, SQLite database, runtime cache, or confirmation/status-card directories;
- containment applied equally to the root, children, verification gates that execute repository code, and any Git hook-capable operations.

As an immediate fail-closed guard, separate the development-only backend from production admission instead of relying on `fixture` alone. Because the worker currently instantiates `UnsafeLocalExecutionBackend` unconditionally, it can reject every non-fake agent before provisioning:

```ts
if (request.agent.kind !== "fake") {
  throw new Error(
    "real Prime execution requires the contained backend; unsafe-local is test-only",
  );
}
```

If disposable local fixtures must remain supported, require a second host-level setting such as `allowUnsafeLocalFixtures`, default it to `false`, reject repositories outside a dedicated disposable root, and ensure the OpenClaw deployment used for those jobs holds no durable provider or infrastructure credentials.

### PD-02: CI executes GitHub Actions through mutable tag references

Severity: **Low**  
Confidence: **High**  
Affected component: GitHub Actions CI supply chain  
Location: `.github/workflows/ci.yml:24`, `.github/workflows/ci.yml:27`, `.github/workflows/ci.yml:30`

#### Vulnerability

The workflow references `actions/checkout@v7`, `pnpm/action-setup@v6`, and `actions/setup-node@v7` by movable tags rather than immutable commit SHAs. GitHub Actions executes these repositories' code on every push to `main` and every pull request. If an upstream tag or its publishing account is compromised, attacker-controlled workflow code will execute before the repository's tests and can forge the result of the quality gate.

#### Concrete data flow

1. A push or pull request triggers `.github/workflows/ci.yml`.
2. GitHub resolves each tag to its current upstream commit.
3. The runner executes that external action code.
4. A compromised action can alter the checkout, dependency installation, test execution, logs, or final job status.

#### Exploitability preconditions

An attacker must compromise one of the referenced action publishers, its release process, or the mutable tag. There is no repository-local input that directly moves these tags.

#### Realistic impact

The principal impact is CI integrity: a compromised action could make malicious code appear to pass the protected `quality` check. Current confidentiality and repository-write impact are constrained because the workflow grants only `contents: read`, the repository is public, no deployment occurs, and no production secrets are configured in the reviewed workflow.

#### Remediation

Pin each action to a reviewed full commit SHA and use an automated updater to propose SHA changes while retaining the human-readable version in a comment, for example:

```yaml
- name: Check out repository
  uses: actions/checkout@<full-reviewed-commit-sha> # v7
```

Apply the same treatment to `pnpm/action-setup` and `actions/setup-node`. Keep the current read-only permissions and do not add secrets to pull-request CI.

## Unverified security concern requiring deployment validation

### Local CLI authority may bypass the owner-only plugin boundary

Status: **Unverified**  
Potential severity: **High**  
Confidence: **Medium that the code trusts local callers; low that an untrusted remote caller can reach it in the deployed system**  
Locations: `src/cli.ts:153`, `src/cli.ts:317`, `src/cli.ts:344`, `src/cli.ts:358`; `openclaw-plugin/src/adapter.ts:556`

The OpenClaw adapter correctly checks owner identity and the original job route before invoking the CLI. The standalone CLI intentionally does not authenticate its caller: it accepts `--owner` as an asserted flag for start/resume and exposes status, result, steer, cancel, jobs, notifications, and notification acknowledgement without transport authorization. This is reasonable only if local process execution is a trusted boundary.

If any non-owner Discord session, shared agent, plugin, or prompt-injected workflow can invoke arbitrary local executables as the OpenClaw OS user, it can call the CLI directly and bypass the adapter's owner and route checks. It could start a fake fixture job with asserted ownership, read job results, steer or cancel existing jobs, or manipulate notification cursors. The repository does not contain the deployed OpenClaw tool allowlist, sandbox policy, or sender authorization configuration, so reachability could not be established.

Validate that:

- non-owner senders cannot reach any generic process, shell, code-execution, filesystem, or delegation tool on this OpenClaw instance;
- the installed CLI and state directory are accessible only to a dedicated service identity, not a general-purpose agent identity;
- other plugins cannot invoke the CLI without independently proving the trusted sender and route;
- local operational use occurs through an authenticated wrapper or a Unix socket with peer-credential checks rather than caller-supplied `--owner` metadata.

If any of these assumptions is false, promote this concern to a confirmed authorization-bypass finding and move authorization enforcement into the control plane rather than relying exclusively on the adapter.

## Defensive posture observations

The following design choices materially eliminate or reduce bug classes and should be preserved:

- `PrimeDispatchAdapter` rechecks owner identity and the immutable original delivery route before read or write operations. Confirmation records are random, single-use, expiration-bound, and context-bound.
- The dispatcher hashes the complete resolved request, including canonical repository path, immutable base SHA, gates, budgets, model policy, and child envelope.
- Subprocesses use argv arrays rather than shell interpolation. Verification gates are stored as command plus argument arrays.
- Repository paths and roots are canonicalized with `realpath`; Git bases resolve to immutable commit IDs; root and child worktree ownership is repeatedly re-proven.
- Worker IPC uses a private Unix socket, bounded messages, a high-entropy nonce, protocol version, PID start identity, and a handshake that must match the durable worker identity.
- The inference broker binds to loopback, uses high-entropy per-lease bearer tokens, binds token and lease ID, fixes the upstream/model/reasoning server-side, rejects redirects, bounds request bodies and SSE parser state, and revokes in-flight requests.
- Runtime archives reject traversal, links, duplicate/unmanifested entries, surprising ownership and modes, excessive sizes, platform/Node mismatches, and content changes before use.
- SQLite operations reviewed use bound parameters or typed Kysely migrations; no attacker-controlled SQL construction was found.
- Artifact paths, cleanup targets, branch identities, worktrees, state revisions, digests, and terminal status are validated again immediately before destructive cleanup.
- Plugin presentation sanitization redacts credential-shaped fields and bounds status content before Discord delivery.

Two defense-in-depth details should be revisited when containment is implemented, but are not independent findings under the current same-user execution model:

- The SDK backend temporarily applies a reduced environment to the worker process but does not delete unrelated existing keys, so OpenClaw location variables inherited by the worker can remain visible to SDK-spawned processes.
- Git wrappers and process-group teardown are bypassable by code that invokes absolute binaries, changes Git configuration, or daemonizes outside the process group. The project documentation already describes these as deterrence rather than security boundaries.

## Scope limitations and items not verified

- No production or third-party system was tested. No exploit payload was sent to a deployed OpenClaw, Discord, Prime, ChatGPT, GitHub, or cloud endpoint.
- Credentialed real-Prime and live OpenClaw lifecycle acceptance tests were not run. Their four test cases remained skipped as intended by the repository.
- The actual deployed host configuration, repository allowlist and fixture labels, filesystem ownership/modes, OpenClaw sender policy, generic tool exposure, firewall, cloud metadata reachability, and egress controls were not available in this repository.
- The pinned Prime Agent and OpenClaw dependency source trees were not independently audited; this review covered how Prime Dispatch packages, verifies, invokes, and constrains them.
- The provider endpoint and Discord/OpenClaw platform authorization implementations were treated as external dependencies.
- Dependency auditing reports known published advisories only; it does not prove the absence of malicious packages or future disclosures.
- The review focused on the current `main` revision and did not audit the full Git history for previously removed secrets.

## Recommended priority

1. Treat OS containment as the production gate. Do not broaden repository use until root agents, children, gates, and Git side effects execute in a dedicated, default-deny security domain.
2. Validate the deployed OpenClaw tool policy to close or confirm the local-CLI authorization concern.
3. Pin GitHub Actions to immutable commit SHAs.
4. After containment lands, run an adversarial dynamic assessment against a disposable host with malicious repository fixtures covering credential reads, state-root writes, egress, process escape, Git hooks, symlink races, and cloud metadata access.
